# Changelog

## Unreleased

## 2.0.1 - 2026-09-21
- The READMEs now list where each package is published and where it is installed (npm `node_modules`, pip `site-packages`, `~/.cargo/bin`), and how to check it. The sample guide opens with what the samples are for and how to try one.
- Rewrite the English and Japanese READMEs, and add a Chinese README, for people deciding whether to use the project: what it does, why, how to try it, and its limits, in plain words. The full technical format matrix moves to `docs/FORMATS.md` and `docs/FORMATS.ja.md`.
- Rewrite the npm and PyPI package READMEs around installing, previewing, reading warnings and safety, and describe the packages in the terms people search for. The package home pages now point to the project site.
- Fix the reusable document preview workflow for other repositories: a caller's pull request no longer tries to build docsvg in the caller's repository or look for the actions there. Only this repository's own pull requests build the proposed docsvg.
- The pull request preview now converts documents whose names contain non-ASCII characters (they were silently skipped), passes names starting with `-` safely, and shows file names, formats and warnings literally in the comment so they cannot add links, images or mentions.
- Update the security policy: private vulnerability reporting is enabled, and packages are published only by manually started workflows with short-lived OIDC credentials. The publication check also recognises npm, PyPI, Slack, Google and AI provider keys.

- Position a tiling pattern's own SVG `<pattern>` element at its `/BBox`'s real origin instead of leaving it hardcoded at `(0, 0)`. A tiling pattern's own content stream draws in absolute BBox-space coordinates (PDF32000 8.7.3.1), which need not start at the origin at all -- a producer is free to declare e.g. `/BBox [35.4 396.6 287.4 588]`, matching wherever on the page the pattern's own designer happened to lay it out. The generated `<pattern>` element's own `x`/`y` set where that content lands within the tile it repeats, so leaving it at `(0, 0)` regardless shifted every BBox with a nonzero origin clean out of its own tile: content clipped correctly to the BBox rectangle, drawn at its own real coordinates, but that rectangle no longer overlapped the pattern's assumed `[0, width] x [0, height]` viewport at all. Found by converting pdf.js's own `22060_A1_01_Plans.pdf`, a fire-safety floor plan whose evacuation-route highlight bands -- all filled with tiling patterns whose `/BBox` origins run into the thousands -- rendered as wrong-sized fragments scattered near the top of the page instead of poppler's correctly sized and positioned bands (sampled pixel difference against poppler drops from 26.2% to 19.8%; a separate, unrelated gap in this file's underlying floor-plan detail remains).
- Stop treating a CID-keyed CFF glyph that resolves to GID 0 as "not found." A CID-keyed CFF's charset conventionally names GID 0 `.notdef`, but nothing in the CFF format actually requires its charstring to be empty -- and a real-world subsetted TeX Computer Modern font (`CMR9`) stores a genuine, fully-drawn "ff" ligature there while its charset still labels it `.notdef` as a formality. The font parser's own reverse CID-to-GID map already signals "this CID has no entry at all" with a dedicated `0xFFFF` sentinel, so treating a resolved GID of exactly 0 as equally invalid discarded a real, drawable glyph outright. Found by converting pdf.js's own `issue11718_reduced.pdf`, whose caption "A different method" rendered without any "ff" ligature at all, falling back to incorrect editable placeholder text for the whole line instead of the real glyph outlines poppler draws.
- Chunk `Identity-H`/`-V` character codes by two bytes when a `CIDFontType0` descendant is backed by a plain Type1 program, instead of iterating one byte at a time regardless. A CIDFontType0 descendant is only ever supposed to carry a bare CFF (`CIDFontType0C`) or OpenType program (PDF32000 Table 126), but some producers embed a plain Type1 program through the simple-font-only `/FontFile` key instead -- and `Identity-H`/`-V` still means each character code is two bytes regardless of what program type backs it (PDF32000 9.7.5.2). This is the same class of bug already fixed for the bare-CFF case in `outline_cff`, just never applied to this sibling Type1 code path: every high zero byte of a CID under 256 showed up as its own spurious one-byte lookup, and the real low byte could then never resolve either once its position shifted by one. Found by converting pdf.js's own `issue11740_reduced.pdf`, whose embedded Cyrillic font (its own built-in Type1 `/Encoding` names each CID's glyph directly by that same numeric code) rendered its "Оглавление" heading as incorrect editable placeholder text instead of real glyph outlines.
- Strip PFB (Printer Font Binary) segment framing from an embedded Type1 font program before parsing it, when present. PDF32000 9.9's own `/FontFile` format is a plain concatenation of a Type1 font's cleartext header, its eexec-encrypted binary portion, and a zero-padding trailer -- no segment framing at all -- but some producers instead embed the raw PFB container format verbatim. Its interleaved 6-byte `0x80 <type> <length>` segment headers land squarely inside the encrypted portion, and since eexec decryption is a running cipher whose state carries across the whole ciphertext, one such header corrupts every glyph's `CharStrings` entry from that point on into garbage -- parsing found none of them at all. Found by converting pdf.js's own `issue14462_reduced.pdf`, whose embedded DejaVuSansMono subset rendered as incorrect editable placeholder text instead of the real "Issue 14462" glyph outlines.
- Resolve a CID-keyed CFF glyph embedded as a full OpenType wrapper (`/FontFile3 /Subtype /OpenType`) through the CFF table's own `charset`, instead of treating the raw CID as a glyph index. That shortcut is correct for a CIDFontType2 (TrueType-based) CID font's raw code under Identity-H/V, but never for a CIDFontType0 (CFF-keyed) one: a CID-keyed CFF's own `charset` maps GID to CID through a font-specific, non-identity table, and an OpenType-wrapped CID-keyed CFF program parses successfully as an ordinary font, so it never reached the existing bare-CIDFontType0C code path that already resolves this correctly. Found by converting pdf.js's own `Embedded_font.pdf`, whose single glyph -- CID 0xA911 -- lives at GID 1 in its two-glyph subset; looking it up as GID 0xA911 directly failed outright, falling back to incorrect editable placeholder text instead of the real glyph outline. The fix detects the sfnt's own `CFF ` table and reuses the CFF parser's existing CID-to-GID reverse map to resolve the correct glyph before handing it to the OpenType outline renderer.
- Decode an `ASCIIHexDecode`-filtered page content stream ourselves instead of relying on lopdf's own decoder, which implements only `FlateDecode`/`LZWDecode`/`ASCII85Decode` for stream content and, by its own documented design, falls back to the RAW (still hex-encoded) bytes on any other filter rather than reporting an error. Fed straight into the content-operator tokenizer, that literal hex-digit text produces garbage tokens -- a spurious bare `A` operator among them -- and the page's real drawing commands are lost entirely. Found by converting pdf.js's own `asciihexdecode.pdf`, whose one line of "Hello world" text rendered as a totally blank page. A new wrapper enumerates a page's content streams directly and decodes a leading `ASCIIHexDecode` layer by hand before handing whatever filters remain to lopdf, preserving lopdf's own lenient raw-bytes fallback for any filter it still cannot decode at all (a real, if unusual, case some corpus files rely on for content using a filter like `JBIG2Decode` that was never meant to be parsed as text in the first place).
- Consult a CFF glyph's own deprecated "seac" composition (Adobe TN#5177 Appendix C): a Type 1/2 charstring can compose an accented letter from two other named glyphs of the same font -- by StandardEncoding code, not by this font's own charset SID or the PDF's `/Differences` encoding -- as `adx ady bchar achar endchar`, instead of drawing its own outline at all. The underlying `stet-fonts` crate's own charstring interpreter already parses this into a `seac` field on its result, but `outline_cff` never consulted it, so a glyph built this way -- its own charstring being pure composition, with no moveto or lineto operators of its own -- produced no outline whatsoever. Found by converting pdf.js's own `endchar.pdf`, named for this exact charstring operator: a single É built this way rendered as a totally blank page, 28.0% of sampled pixels differing from poppler's own rendering, the single worst result across a fresh visual-diff sweep of the whole corpus.
- Draw a Link annotation's own fallback border (from its `/Border` or `/BS` width, and its `/C` colour) when it has no `/AP` appearance stream of its own. PDF32000 12.5.4 leaves this entirely to the reader's discretion, and poppler draws one whenever a document explicitly declares both a positive border width and a colour -- which this now mirrors, narrowly: the overwhelmingly common case is a Link with neither set at all (most real documents rely on the *absence* of a visible border here), so a Link with no width or no colour still draws nothing, and a Link's own `/AP`, on the rare occasion it has one, is still never drawn either way, preserving the deliberate existing choice that a Link is conventionally just an invisible active area. Found by converting pdf.js's own `file_url_link.pdf`, whose link text is meant to sit inside a visible green border box -- poppler draws it, this converter drew nothing at all.
- Recognize an inline image's own `/IM` (`/ImageMask`) flag. - Resolve an Indexed color space's palette entries through the same conversion used for painted colors, instead of assuming they are already raw sRGB or CMYK bytes whenever they happened to have 3 or 4 components. An Indexed space's base can legally be anything -- Lab, CalGray, CalRGB, Separation, DeviceN or ICCBased, not only DeviceRGB/Gray/CMYK -- and a 3-component Lab base is common enough to collide with the old "3 components means RGB" assumption; Lab's own components additionally need denormalizing from a raw `0..255` palette byte into their own much wider native scale (L* in `[0, 100]`, a*/b* in the space's own `/Range`) before conversion, not a flat divide by 255. Found by converting pdf.js's own `issue10339_reduced.pdf`, a Lab-indexed image that rendered as a muddy brown instead of the intended blue (68.9% of sampled pixels differed from poppler's own rendering; only the color was wrong, not the shape, since the palette lookup itself -- and this file's own `/Decode`-array palette-index inversion -- were otherwise already correct).
- Dereference a page's own `/MediaBox`, `/CropBox` and `/Rotate` before checking their type, the same class of fix as the `/OCProperties` dereferencing gaps elsewhere in this changelog. Any of these can legally be an indirect reference rather than an inline value, and reading one with a non-dereferencing dictionary lookup before checking its type silently treated it as absent, falling all the way back to this converter's own default of a US Letter page (612x792pt) regardless of the PDF's real page size. Found by converting pdf.js's own `bug852992_reduced.pdf`, whose real, much smaller and negative-origin 540x190pt page -- itself sharing one indirect array object as the `/MediaBox` and as several unrelated Form XObjects' and shadings' own `/BBox`, which is what exposed the gap -- squeezed all of its actual content into a small corner of a mostly blank default-sized canvas (77.1% of sampled pixels differed from poppler's own rendering; the page is pixel-identical to poppler's own rendering with this fix).
- Resample a PDF image and its own soft mask to a common resolution instead of dropping the mask outright whenever their pixel dimensions differ. Per spec each is independently mapped onto the same unit image square, so they need not share a native resolution at all -- and in one common real-world pattern they deliberately do not: a solid, uniformly-coloured base image at a tiny resolution (as small as 1x1) paired with a full-resolution soft mask that alone carries the shape of whatever is actually being drawn. Found by converting pdf.js's own `chrome-text-selection-markedContent.pdf`, whose text-selection highlights are exported by Chrome exactly this way -- a 2x2 solid-colour base image, and a soft mask sized to the actual glyph run that carries the highlight's real, per-glyph shape entirely in its alpha channel; discarding the mask on a size mismatch, as a same-dimensions check did, left every highlight either solid or altogether missing rather than glyph-shaped. Downsampling the mask down to the base image's own tiny resolution would have been just as wrong, throwing away exactly the detail the mask exists to carry -- so the two are now nearest-neighbor resampled up to their larger common resolution before being combined into a single RGBA raster.
- Decode a Type3 glyph's own CharProc, a Form XObject, a tiling pattern and a soft mask's group content through the same inline-image-aware content-stream scanner the top-level page already used, instead of handing them straight to `lopdf::content::Content::decode`. That generic parser has no notion of `BI...ID...EI` inline-image syntax at all -- it is not equipped to skip over the image's own raw binary sample data, which routinely contains byte sequences that look like other PDF tokens -- so any inline image nested in one of these silently corrupted parsing of that entire content stream, discarding not just the image but every operator after it. Found by converting pdf.js's own `bug1245391_reduced.pdf`: a Type3 glyph's CharProc drew an inline image bitmap as part of the glyph shape, and the corrupted parse turned the file's only content into a 57-byte page that drew nothing at all. Fixing this in turn exposed a second, previously unreachable defect in the scanner itself: it looks for a literal `EI` token to end the image data, requiring the byte immediately before it to be a PDF delimiter (to avoid matching a stray "EI" inside binary noise) -- but the PDF spec recommends, and does not require, a white-space separator between an inline image's last data byte and `EI`, and real-world encoders often omit it. An *unfiltered* image's own dictionary (width, height, bits per component, colour space) determines its exact row-padded byte length regardless, so the scanner now checks that exact position for `EI` first, before falling back to the generic scan. Found by the same corpus run once the CharProc/Form/pattern/mask fix above started routing many more real-world inline images through this code path for the first time: `bug1513120_reduced.pdf` (a Type3 font whose glyph bitmaps are all built this way) and `issue10388_reduced.pdf` (a single 16x17 stencil mask) both failed outright, the latter aborting the whole page's conversion rather than merely warning.
- Draw a filled rectangle with zero width or zero height as a thin stroke instead of a literal zero-area (and so invisible) fill. Real-world PDFs -- CAD exports, ruled grids, table borders -- commonly use exactly this to draw a hairline instead of stroking it, relying on every mainstream viewer's rasterizer to give a degenerate fill a sliver of coverage; a vector SVG output has no such rasterizer convention to lean on; a truly zero-area path is simply invisible. Found by converting pdf.js's own `issue4260_reduced.pdf`, a page built entirely from zero-height and zero-width filled rectangles forming a ruled grid, which rendered as a totally blank box. The conversion is deliberately narrow: only a path that is nothing but a single `re` rectangle, filled but not stroked, with exactly one of its two dimensions exactly zero, is affected -- an ordinary rect, a zero-area point, or a path that already carries its own stroke is left alone.

- Map an annotation appearance's `/BBox` to its `/Rect` only after first applying the appearance's own `/Matrix` to `/BBox`'s corners, per PDF32000 12.5.5's algorithm. `/Matrix` commonly carries a real translation -- it is exactly what lets a PDF producer normalize an appearance's content near the origin while declaring `/BBox` and `/Rect` equal -- and that translation must be cancelled by the BBox-to-Rect mapping, not left in the combined transform. Mapping straight from `/BBox`'s own (untransformed) values instead left `/Matrix`'s translation in place on top of it, doubling the offset and drawing the whole appearance somewhere other than inside `/Rect`. Found by converting pdf.js's own `file_pdfjs_test.pdf`, whose "this is a text annotation" FreeText annotation rendered at the bottom of the page instead of just below the title, where poppler correctly draws it.

Dereferencing `/OCGs` before checking whether the result was an array correctly unwrapped an indirectly-referenced *array*, but for this single-OCG form it resolved straight through to the OCG's own dictionary, discarding the object ID the hidden-group lookup needs to work at all -- so a Form XObject's own `/OC` entry (as opposed to a content-stream `BDC /OC` wrapper) naming an OCMD with a bare single OCG reference always rendered as visible, regardless of that OCG's real default state. Found by converting pdf.js's own `issue12007_reduced.pdf`: unrelated source-material images (a pet photo, an image editor's own UI chrome) meant to stay off by default were rendering on top of the one line of text the page was supposed to show.

- Stop refusing to outline a symbolic simple TrueType glyph just because its character code is missing from the font's `/ToUnicode` CMap. A symbolic font (no `/Encoding`, symbolic by the PDF spec's own default) resolves glyphs through its own embedded cmap by raw character code, never through Unicode, so a missing `/ToUnicode` entry says nothing about whether the glyph exists -- but a missing entry there was still treated as "this code cannot be resolved at all," aborting before the font's own cmap, tried by raw code first for exactly this reason, ever got to run. Found by converting pdf.js's own `issue2017r.pdf`, a font specimen sheet whose symbolic embedded TrueType font fell back to incorrect placeholder text. - Dereference `/OCProperties /D /OFF`, `/ON`, the top-level `/OCGs` array, and an OCMD's own `/OCGs` member list before checking whether each is an array. - Gamma-encode `CalGray` into sRGB instead of returning its raw luminance directly. `CalGray`'s `A^Gamma` is a linear luminance the color space's CIE `WhitePoint` scales, not a value already fit to use as an sRGB pixel; returning it as `[A^Gamma, A^Gamma, A^Gamma]` skipped the sRGB gamma-encoding curve that `CalRGB` and `Lab` already apply via this converter's own `xyz_to_srgb` helper, rendering every midtone far too dark. Found not by a warning -- there wasn't one -- but by a systematic visual diff against poppler's own rendering across the entire pdf.js test corpus: pdf.js's own `calgray.pdf` stood out with 73% of sampled pixels differing from poppler's reference, far more than any other file, while its layout, text and structure matched exactly. The direct fix -- routing `CalGray` through the same `xyz_to_srgb` matrix `CalRGB`/`Lab` use -- corrected the lightness but introduced a visible color tint, because that matrix assumes a D65 white point and this file declares an unusual equal-energy `[1 1 1]` one; `CalGray` is inherently achromatic by construction (X, Y and Z are always the same white-point-scaled luminance), so the correct fix gamma-encodes the luminance directly into a neutral `R=G=B` instead, sidestepping any white-point mismatch entirely. `calgray.pdf`'s diff against poppler drops from 73% to under 2%.
- Resolve a Type0 font's CID-keyed CFF glyphs by two-byte CID under Identity-H/V, instead of one byte at a time. A bare CIDFontType0C program has two-byte character codes under Identity-H/V, but `outline_cff` iterated the raw bytes one at a time regardless of font kind -- so every high byte of a two-byte CID under 256 produced its own spurious, always-failing "code 0" lookup, and even the low byte could never resolve through the name-/Unicode-based lookup meant for simple fonts, since a CID-keyed CFF's own charset maps GID to CID rather than to a name. Found by converting six different pdf.js corpus files that all shared this exact recurring warning (`bug1937438_mml_from_latex.pdf`, `bug1947248_text.pdf`, `cid_cff.pdf`, `doc_3_3_pages.pdf`, `highlight.pdf`, `issue18408_reduced.pdf`), traced to their common shape: `/Subtype /CIDFontType0C` under `/Encoding /Identity-H`. `outline_cff` now chunks its input by two bytes and resolves the glyph directly through the CFF parser's own CID-to-GID reverse map when the font is Identity-keyed, the same pattern the TrueType/CIDFontType2 fix above already uses. - Fall back to a TrueType font's own `post` table when it has no `cmap` table at all to search. A simple, non-symbolic font can legally ship with no `cmap` table -- unremarkable for one subsetted to be looked up only through the PDF's own `/Differences` (or base) encoding, since nothing about that requires a cmap. `outline_path` only ever tried Unicode-character-based cmap/charmap lookups, though, which had nothing to search in that case and failed outright for every glyph, falling back to incorrect placeholder text for the whole font. Found by converting pdf.js's own `TrueType_without_cmap.pdf`, whose embedded "Masis" font has no `cmap` table but does carry a version-2.0 `post` table with real glyph names. - Resolve a Type0 font's Identity-H/V glyphs directly by CID instead of through the embedded font's own cmap. Under Identity-H/V the raw character code already *is* the CID (PDF32000 9.7.5.2), and with no `/CIDToGIDMap` the CID *is* the GID directly -- no cmap lookup involved at all. This converter instead routed every CID font through the same Unicode-character-based cmap lookup used for simple fonts, which fails whenever a subsetted CID font's embedded cmap lacks full Unicode coverage: a common case, since a subsetter is free to ship a minimal or absent cmap once glyph selection no longer depends on it. Found by converting pdf.js's own `basicapi.pdf`, whose subsetted embedded DejaVuSans and DejaVuSans-Bold fonts failed on perfectly ordinary ASCII letters ('C', 'P') and fell back to incorrect placeholder text; visually comparing the rendered page against poppler's own output, before the fix, showed the difference directly. `FontDecoder` now resolves an Identity-H/V font's glyph via its own `/CIDToGIDMap` (or the `/Identity` default) directly, bypassing cmap -- and, incidentally, making this path immune to `/ToUnicode` gaps the same way the CFF/Type1 fix below already is.
- Decode a PDF image stream's leading compression filters before handing it to its own image codec. Found by converting pdf.js's own `comments.pdf` test file, whose `Im0` image sets `/Filter [/FlateDecode /DCTDecode]` -- Flate wrapped around a JPEG purely for a little extra compression, which is legal and not unusual.
